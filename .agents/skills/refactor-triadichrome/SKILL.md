# Triadichromeの全面リファクタリング

毎回、現在のリポジトリ全体を調べてから再構成を設計する。利用者ができること、操作の結果、開けるファイル、保存される内容を維持し、責任の混在・重複・不要な依存を解消する。ファイル分割や新しいフォルダを作ること自体を成果にしない。

製品判断は[REQUIREMENTS.md](../../../REQUIREMENTS.md)、作業・権限・検証・コミットは[AGENTS.md](../../../AGENTS.md)、実装済み範囲とコマンドは[README](../../../README.md)に従う。

## 依頼の扱い

- 対象はアプリ全体のすべて。構造、状態とデータの流れ、画面内部、計算、保存、履歴、安全性、性能、依存ライブラリ、生成・検証・文書を横断する。必要なら内部を全面的に作り直し、既存の骨格へ合わせることを優先しない。
- 全面リファクタリングの実行依頼では、全体調査と設計を行い、利用者の明示的な承認後に呼び出し元の移行、検証、置換後の整理、必要な文書更新と通常コミットまで進める。
- 調査・設計・レビューだけの依頼では読み取りと設計を行う。設計結果から実装の許可を推定しない。
- 対象や除外が指定されていれば保持する。全体の依存関係を調べることと、対象外を編集することは別である。
- 現在の機能・表示・操作・保存データ・受け付けるファイルを維持する。依存ライブラリと開発・検証の仕組みは、必要性と効果を裏付けられる更新・置き換えも設計対象にする。
- 既存の不具合は勝手に修正しない。[判断を仰ぐ報告と分担](references/decisions-and-review.md)に従い、専門知識がなくても判断できる説明を行う。要件の未実装、要件と実装の矛盾、今回の変更による不具合を区別する。

## 1. フルスキャンを完了する

[全体調査と検証](references/full-scan-and-verification.md)に従い、隠しフォルダを含むプロジェクト全体を棚卸しする。自作のコード、CSS、設定、スクリプト、テスト、文書は全文を分割して読み、入口から保存・再読込・画面表示まで追う。全文検索や件数だけで全文読了と扱わない。

一覧には各領域の所有者、依存先、保持する動作、テスト入口、生成方法を対応させる。未読・未確認・読み取り失敗を残したまま全体調査完了としない。依存パッケージ、Git内部情報、キャッシュ、生成物は同参照の扱いに従う。

候補ごとに、現在の根拠、具体的な変更負担や危険、影響する利用者向けの動作、呼び出し元、既存検証を整理する。候補は「変更が必要」「現状維持」「根拠不足」「対象外」「利用者判断待ち」に分け、全領域に判断を付ける。古い名称、行数、似たコードだけで削除や共通化を決めない。

## 2. 責任と依存を設計する

[再構成の設計](references/architecture.md)を読み、次を具体化する。

- 保存済み計画、未保存の入力、履歴閲覧、画面移動、表示位置を誰が保持し、いつ変更・破棄できるか。
- 金額と種別の規則、表の計算、SQLiteの読込・検証・更新、実ファイルへの確定をどこで分けるか。
- 画面と共通操作、各マスタの固有制約、CSSと動きの設定、拡張入口、生成と検証の責任。
- 変更前後の依存方向、移動先、呼び出し元の移行順、失敗時の保護、置換後に除去する経路。

既存のcoreとextensionの境界を維持し、その内部に必要な単位を設ける。具体的なフォルダ名と分割数は実行時の根拠で決める。責任の重複、依存の逆転、変更が広がる原因が減ることを、変更前後の呼び出し関係と実際の変更例で評価する。新しい状態管理や保存の仕組み、ライブラリの更新・置き換えは、現状維持案と効果、移行負担、互換性、配布物、ライセンスを比較する。最新であることだけを導入理由にしない。版やAPI、保守状況は公式情報で確認し、プロジェクトの依存管理規則に従う。データベースの開閉・検証・export、byteの複製、再計算、描画、購読の増減も見積もり、構造整理で通常操作の処理負担を無用に増やさない。

全体調査後、[判断を仰ぐ報告と分担](references/decisions-and-review.md)に従って全体設計を提示する。利用者の明示的な承認を待ち、それまでは製品ソース、依存、設定、生成物を変更せず、調査・設計・レビューを進める。実行依頼やスキルの呼び出しだけを全体設計への承認とみなさない。承認後は範囲内の通常判断を任せて進める。重大な設計変更、既存不具合の修正、AGENTS.mdで確認が必要とされる未承認の変更は、その部分について判断を仰ぐ。

## 3. 段階的に置き換える

現在の依存関係から、各段階で検証できる順序を選ぶ。先に動作と失敗経路の基準を確保し、共通の計算・型、データ処理、保存の制御、画面状態、各画面・CSS、ビルド・テストの順を必要に応じて調整する。途中で正常に使えない状態を別の完了コミットとして切り出さない。

一つの変更単位では責任の移動と呼び出し元の接続を完結させる。全体調査で挙げた対象を追い、最初の大きなファイルの整理だけで終了しない。独立した目的はプロジェクトのコミット規則に従って分ける。

置換後は旧関数・型・ラッパー、イベント、タイマー、CSS、動的参照、Manifest、ビルド入口、テスト、文書を再走査する。利用先や現行の保存契約が残るものを消さない。一時的な橋渡しを置く場合は、必要な理由と除去条件を設計に示し、今回の対象なら移行を完了して取り除く。

調査とレビューは、利用可能な複数のサブエージェントへ読み取り専用で分担する。編集、統合、検証コマンドの実行、Git操作は主担当がまとめる。分担と独立レビューの手順は[判断を仰ぐ報告と分担](references/decisions-and-review.md)に従う。他チャットへの連絡、ブランチ作成、並行編集の許可へ広げない。

## 4. 結果を確かめて完了する

[全体調査と検証](references/full-scan-and-verification.md)の保持条件に対して、既存検証の実際の内容と不足を照合する。必要な回帰検証を追加し、標準検証、画面への影響に応じたCodex内のブラウザ確認、生成物と文書の参照確認を完了する。

既存テストの入口やファイル配置に結び付いた検査は、新しい構造でも同じ動作を検証する形へ移行する。失敗を隠すための削除・期待値変更、未実行テストを実行済みとする報告は行わない。

設計のみの完了条件は、全体の依存と保持条件、根拠のある変更単位、移行順、検証方法と未確定事項を示すこと。実行依頼の完了条件は、全調査領域の判断、対象内の再構成と呼び出し元移行、不要経路の除去、保持条件の検証、文書・生成物・版の一致、通常コミットが揃うこと。承認された対象に残る根拠不足や検証失敗は完了扱いにしない。利用者が修正を見送った既存不具合と対象外は、判断と残る影響を明記して区別する。報告では構造がどう改善したか、維持できた結果、検証と限界、コミットと残存差分を簡潔に示す。
