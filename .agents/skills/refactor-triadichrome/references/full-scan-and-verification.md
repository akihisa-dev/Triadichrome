# フルスキャンと動作保持の検証

## 全体調査の対象

Git状態とHEAD、通常・cached差分を確認した後、`git ls-files`と`rg --files --hidden`を使い、Git管理対象とディレクトリに実際に存在するものを照合する。無視されたフォルダも存在・用途を確認する。依存パッケージやキャッシュを除外した検索結果だけでプロジェクト全体の一覧としない。

| 領域 | 読み方と確認する関係 |
|---|---|
| 自作のコード・CSS | 全文を適切な大きさに分割して読む。import/export、型だけの依存、動的参照、イベント、タイマー、資源と状態の所有者を追う |
| 設定・スクリプト・フック | 全文を読み、入口、生成先、同期・削除範囲、環境変数、実際のコマンドの依存を確認する。調査のために外部変更や画像制作を起動しない |
| テスト・fixture・サンプル生成元 | 全文を読み、実際のassertion、起動入口、製品コードとの共用、失敗条件、固定値、実行されていない検査を照合する |
| 製品・設計・開発・Skillsの文書 | 自作のプロジェクト文書を全文確認する。規範と実装済み範囲、古い説明、参照切れを区別する。スキルを読むこと自体は実行の許可にしない |
| packageとlockfile・依存 | 設定とlockfileの全項目を確認し、実際に使用する依存・直接と間接の関係・版とライセンス・開発と配布の境界を追う。インストール済み依存の全ソースを無条件に読む必要はない |
| 配布用の生成物 | Manifest、独立ページ、service worker、JS・CSS・画像・WebAssemblyの入口と参照を確認する。生成物を正本として編集しない |
| 画像・専用ファイル | メタデータ、生成元と利用先を確認する。見た目が判断に関係する画像は表示して確認する。SQLiteは読み取り専用で形式、schema、制約、件数、整合性を調べる |
| Git内部情報・キャッシュ・過去の検証出力 | 用途と現在の作業との関係を確認する。Gitの全object、依存キャッシュ、OSの管理ファイルは製品コードの全文読了対象に数えない。過去結果は対象状態と条件が一致した場合だけ再利用する |

全文を機械的に読み込んだ件数、import抽出、テスト名一覧は補助であり、コードを読んだことの代わりにしない。ツール出力が省略されたら未読範囲を分割して読み直す。環境固有の秘密情報を全文表示する必要はない。未管理ファイルは所有・用途を確認し、今回の対象と安全に分離できないものを変更しない。

スキャンの結果には、各領域の対象・確認方法・未確認理由、責任と依存の図または表、保持する契約、変更候補と根拠を含める。これらは作業中の設計として簡潔に扱い、作業履歴を恒久的な製品文書へ蓄積しない。静的な調査と実行して成功した検証は区別する。

## 検証の選び方

最初に、通常テストと画面テストの入口から実際にどの検査が実行されるかを確認する。既存の成功結果を利用できない場合は、変更前の基準を必要な範囲で確保し、既存不具合と今回の回帰を分ける。

移動する契約に既存の十分な検査があれば再利用する。追加する検査は保存成功・失敗時の結果、数値・順序・識別の保持などを確認し、ファイル名や関数分割そのものを期待値にしない。保存内容は意味のあるschema・データ・識別子・revisionを比較し、必要のないSQLite内部のbyte一致を要求しない。外部変更の検知などbyte一致が契約である箇所はその検査を保つ。

画面を再構成したときは、Codex内のブラウザで製品と同じプレビューを操作する。自動の画面テストを追加実行する場合は、その必要性と実行内容を示し、プロジェクトの任意検証として扱う。実ファイル・ストア画像・実サイト・性能の確認はAGENTS.mdの実行範囲に従う。

変更単位の検査が通ったら、最終状態で標準の`npm run verify`と必要な画面確認、生成物・参照・差分を確認する。同じ状態での成功結果を重複実行しない。検証が失敗したら、環境不足・既存失敗・今回の変更による失敗を分け、必要な修正だけを行う。

型検査とbuildだけで保存失敗や利用操作を検証したとは扱わない。メモリ内のファイル代替で実ファイルの耐久性や実際の許可を保証しない。ブラウザ起動失敗、未読領域、未移行の利用先、根拠不足の削除候補を残して完了にしない。
