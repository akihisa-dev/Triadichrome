# 利用者の判断と読み取り専用の分担

## 全体設計への承認

全体を調べた後、次の内容を一つの全体設計として提示する。専門用語を先に並べず、変更の目的と利用者・開発者に起こることから説明する。技術的な根拠は必要な箇所へ添える。

- 現在どこで責任が混在し、変更や失敗への対応が難しくなっているか。具体的な操作や変更例を示す。
- 全領域について、作り直すもの、残すもの、それぞれの根拠。フォルダ図だけでなく、処理とデータが誰から誰へ渡るかを示す。
- 機能・見た目・操作・保存データ・ファイル互換性をどう維持するか。
- 使用技術や開発・検証の仕組みを更新・置き換える案、その効果、移行の負担、見送る案との違い。
- 変更の順序、各段階で使える状態、検証方法、通常コミットまでの完了条件。
- 性能と安全性の評価根拠、未確認事項、既存不具合と利用者の判断が必要な事項。

最後に全体設計への承認を求める。回答が来るまで製品の実装に着手しない。部分承認なら対象と保留部分を区別する。設計の承認を、不具合修正や保存形式・権限・公開先などの変更の包括承認にしない。

承認後に設計が大きく変わる場合は、前の案から何が変わり、効果と影響がどう変わるかを提示し、その部分の判断を待つ。通常の内部実装判断で承認を繰り返さない。

## 既存の不具合を報告する

発見だけで修正へ進まない。再現手順、現行要件とコード、確認結果から、既存の不具合か、仕様上の動作か、未確定かを判断する。利用者向けの本文は次の形にする。

1. **何が起きるか**：どの画面でどんな操作をすると、期待と違う何が起きるか。
2. **何が困るか**：入力、計算、表示、保存データへの影響。起きる条件と頻度が不明なら、その点も示す。
3. **確認できたこと**：再現した結果と確認できていない範囲。内部名やログだけで説明を終えない。
4. **修正する場合**：何が改善し、現在の動作のどこが変わるか。他への影響、互換性、確認の負担。
5. **修正を見送る場合**：何が残り、今回の再構成を独立して進められるか。
6. **推奨と判断事項**：理由を添えて、修正する・見送る・追加調査のうち必要な選択を求める。

例えば「保存後に古い結果で入力が置き換わるため、保存中に入力した内容が画面から消える」のように、利用者の操作と結果で説明する。専門用語が必要なら意味を先に説明し、コードの位置や技術的な原因は補足へ置く。この例を実在する不具合として報告しない。

複数の独立した問題を一括承認させず、判断は一件ずつ行う。修正の承認を待つ間も、その不具合に依存しない調査・承認済みの再構成は進める。構造上の改善へ混ぜて黙って修正しない。

今回の変更で新たに起こした不具合は、既存不具合として承認待ちにせず、承認済みの動作へ戻す修正と再検証を行う。新旧を判別できない場合は根拠を補ってから報告する。テストを弱めたり要件を書き換えたりして失敗を隠さない。

## 複数エージェントで調査とレビューを行う

主担当は全体の責任を持ち、実行時の利用可能な枠に合わせて分担する。既存チャットへ連絡することとは区別する。利用できない場合は主担当で必要な確認を行い、独立レビューができなかった制限を報告する。

- 調査担当：計算とSQLite、保存と履歴、画面・状態・CSS、ビルド・依存・テスト・文書など、実際の規模に応じて領域を分ける。対象ファイルの全文、利用先、保持条件、問題の根拠、未確認範囲を読み取り専用で調べる。
- 主担当：担当間の境界、漏れ、矛盾を照合し、横断する処理を自分でも追う。要約の受け取りだけで全体を読了したと扱わない。設計を統合し、利用者への報告と判断の記録を所有する。
- 設計レビュー担当：根拠と保持条件から、全体設計の漏れ、責任や依存の逆転、過剰な共通化、保存と移行の危険、性能負担、実行できない検証を独立して確認する。指摘を主担当が判断し、修正した全体設計を利用者へ提示する。
- 変更レビュー担当：承認設計、対象差分、検証結果を読み、維持する動作、旧利用先の残存、失敗保護、依存と生成物、テストの弱体化を確認する。対象HEADと差分を指定し、途中で変化した範囲は結果を流用しない。

すべての分担で編集、build、依存更新、ステージング、コミット、外部変更を禁止する。検証を提案する担当と、実行する主担当を分ける。レビュー中に検証可能な状態を変えない。主担当だけが最新の差分を再確認して編集・統合・コマンド実行を行う。

レビューの指摘は事実、影響、根拠を確認して対応する。既存の不具合修正はレビュー担当の提案だけで承認済みと扱わず、利用者へ判断を仰ぐ。レビュー結果が出るまで、必要な独立レビューを完了したとは報告しない。
