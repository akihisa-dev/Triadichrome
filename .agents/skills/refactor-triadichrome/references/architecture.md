# 責任と依存関係の再構成

これは設計の判断基準と調査の入口であり、現在の構造を固定する移動指示ではない。実行時に現行コード、正本文書、利用先を再確認する。製品の計算や操作を説明する正本は[製品要件](../../../../REQUIREMENTS.md)と[データモデル](../../../../DATA_MODEL.md)にある。

## 基本の分け方

| 責任 | 依存の考え方 | 確定するもの |
|---|---|---|
| 業務の規則と型 | core内。React、Chrome、ファイル参照、SQLの接続へ依存しない単位を検討 | 金額の精度、年度・月、種別の引き継ぎ、入力制約、分類・科目の意味 |
| 表示用の計算 | 業務の規則と保存済みのデータから求める | 三表・施策一覧・明細の数値と安定した順序 |
| SQLiteの処理 | core内。規則を利用し、接続・SQL・検証・複製を所有 | 有効なバイト列と読み取り結果。ブラウザの保存成功とは分ける |
| 計画を開いている間の制御 | extension内。coreとブラウザ処理を組み合わせる | 現在の計画、保存の順序、履歴期限、過去閲覧、終了可能な状態 |
| ブラウザ処理 | extension内。具体的なブラウザAPIを所有 | 選択、許可、ファイル参照、読み書き、前回ファイルの記憶 |
| 画面と入力操作 | extension内。計画制御へ編集を依頼する | 下書き、選択、画面移動、フォーカス、スクロールと表示 |
| ビルドと検証 | 正本から生成し、製品と同じコードを使う | 配布物、テスト用の境界、検証コマンドと対応する文書 |

例えばcore内を業務規則・表計算・SQLiteへ、extension内を計画制御・ブラウザ処理・画面・共通操作へ分けられる。フォルダ階層は責任と実際の依存に必要なものだけ作る。型の共通化のために全領域が一つの巨大なモジュールへ依存する構造に戻さない。

画面から計算と保存の詳細を追い出すだけでなく、更新依頼から検証・書き込み・保存済み状態の公開までの責任を一つにつなぐ。制御モジュールから画面を逆に読み込まない。sql.jsの初期化とWebAssemblyの配置はデータ処理の境界で扱い、service workerへReactやDOMの依存を持ち込まない。

## 現行構造で追う入口

- `extension/ExtensionPage.tsx`：入口、選択・ドロップ・新規作成、前回ファイル、計画参照、保存、履歴期限、終了。
- `extension/HomePage.tsx`：画面移動履歴、登録前の下書き、保存済み内容、過去閲覧、編集による移動禁止、マスタと施策の更新。
- `core/initiatives.ts`：計画全体の読込、施策の型・検証・登録・更新、種別別の金額と属性別の計算。
- `core/kindAmounts.ts`、`core/planTables.ts`、`core/details.ts`：種別解決、前年の合算、三表の計算、明細の識別と編集。
- `core/triadicSchema.ts`、関連Schema、`triadicDatabase.ts`、`triadicMigration.ts`、`migration10.ts`：現行形式の生成・検証と名前の歴史。
- `core/autoSave.ts`、`extension/useAutoSave.ts`、`planFile.ts`、各`*File.ts`、`triadicFile.ts`：入力待機から実ファイル確定まで。
- `core/dataHistory.ts`、`dataHistorySchema.ts`、`extension/DataHistoryPage.tsx`：時点記録、閲覧、復元、削除。
- 各`*MasterPage.tsx`とcoreの対応マスタ：似た操作と固有の入力・削除制約。
- 施策と前年の`*AmountGrid.tsx`、対応するcoreのGrid：選択、編集、貼り付け、セル移動の共通部分と相違。
- `HomeRelationsPage.tsx`、`AggregationGraph.tsx`と関連hooks：表示だけの移動と、保存対象の所属変更の違い。
- `ExtensionPage.css`と個別CSS：共通設定、画面固有の寸法、親要素を変える指定、重ねた指定の適用順。

パスを移したらこの入口一覧と正本文書の参照も更新する。存在を確認せず、一覧を現在の実装済み範囲の証明にしない。

## 状態の所有と保存成功

保存済み計画の正本を明確にし、画面用コピーとファイル用コピーが別々に新しい状態を確定しないようにする。編集中の入力は保存済み状態と分け、保存中の追加入力を古い保存結果で置き換えない。

更新を次の流れで追い、責任を分離しても順序を保つ。

1. 入力全体と編集対象を検証し、元の計画を変更しないコピー上で次の状態を作る。
2. 必要な履歴を同じ保存へ準備し、書き込み先の外部変更を確認する。
3. 実ファイルの書き込みとcloseによる確定を完了する。
4. 保存成功した状態だけを現在の計画として公開し、より新しい入力は次の保存に残す。

入力の遅延、保存の直列化、排他制御はそれぞれの目的と所有者を定める。履歴記録・通常保存・復元・削除・終了の競合を、別々のbusyフラグの追加だけで防ぐ設計にしない。常時開いたデータベースや新しい保存キューへ変える場合も、コピー上の処理、失敗保護、資源解放を同等に確保する。

現在の計画、過去閲覧用の計画、登録前の下書き、既存データの編集、画面移動履歴、相関図の配置は別の寿命を持つ。ファイル終了、画面移動、過去閲覧開始、現在への帰還、復元成功のそれぞれで、保持・破棄・初期化するものを定義する。

## 共通化と除去

マスタの名称編集・自動保存・確認付き削除などの共通操作はまとめられる。科目の順序、コード検証、必須集計、使用中判定、固定種別を共通部品の都合で同じ規則へ変えない。

入力表の範囲選択や移動は、DOMのイベント処理とcoreの一括更新を分けて検討する。前年の集計行と施策の編集禁止月など、移動先・入力可能なセルの違いを明示的に渡す。二つの表を多数の条件分岐を持つ一つの巨大部品へ置き換えるだけで終えない。

相関図の表示操作と集計の所属変更は同じドラッグでも意味が違う。座標処理の共通化で、保存対象・フォーカス・位置保持・動きが変わらないようにする。

旧形式に見える定義でも、現行形式の新規作成、拒否用fixture、SQLビュー、履歴snapshotが利用している可能性がある。受け付ける形式、生成するschemaと制約、現行の表・ビューの参照を照合してから置き換える。現行形式の組み立てに必要な旧定義は、直接生成する定義へ移行して同等性を確かめるまで消さない。

似た計算、未使用のexport、常に失敗する更新経路、実行入口のないテストは調査候補とする。テスト専用の利用先も確認し、必要な検査は新しい入口へ接続する。動いていない検査をそのまま復活させ、古い仕様を製品へ戻さない。

CSSは全体へ効く設定と部品の設定を分け、読み込み順・詳細度・幅別の上書きを確認する。見た目、固定列、スクロール範囲、通知と入力欄の位置、途中で反転できる動きを維持する。

READMEと製品要件に合う現在の仕様を基準に、古い設計文書の食い違いを解消する。要件未実装の機能を加えることや、現在の不具合を要件へ合わせて正当化することを文書整理に混ぜない。
