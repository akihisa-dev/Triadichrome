# データの時点履歴の設計

利用者向けの動作は[製品要件](../REQUIREMENTS.md#データの時点履歴)、使い方と制限は[README](../README.md#データの履歴)を正本とする。履歴は同じ`.triadic`内で計画全体を記録し、通常の画面で内容を確認してから復元できるようにする。

## 保存構造

保存形式13に任意の履歴管理表を追加する。履歴のない現行ファイルは開く際に変更せず、最初のデータ変更の保存に履歴表と変更前の記録を含める。計画本体の表・ビュー・計算規則は維持する。

| 保存先 | 内容 |
|---|---|
| `data_history` | 削除後も再利用しない識別子、UTCの記録日時、履歴表を除いたSQLiteの計画全体 |
| `data_history_state` | 履歴管理の版1、次の識別子、最初の未記録の保存日時、最新のデータ保存日時 |

履歴の作成ではコピーから履歴表を除き、不要領域を詰めてから保存する。過去の履歴を各記録へ複製しないため、容量の増加は計画本体の大きさと記録件数に応じる。追加の依存パッケージ・拡張権限・通信は不要とする。

日時・識別子・管理版・SQLiteの識別情報はファイル読込時に検証する。個々の計画の全体検証は選んだ履歴の読込時に行い、現在の計画と同じ年度であること、履歴を入れ子に含まないことも確認する。大量の記録を開くたびにすべて復号・展開しない。

## 記録と保存境界

すべてのデータ更新は`writePlanChange`で履歴の未記録状態を更新する。初回は変更前の状態も準備する。保存先の外部変更を確認し、書き込みと確定の成功後だけ現在の計画を置き換える。失敗した更新の履歴だけが残る状態にはしない。

`ExtensionPage`は保存済みの未記録日時から5分の期限を求める。一連の保存で期限を延ばさず、同時のファイル処理があれば終了後に記録する。記録中に始まった自動保存はその書き込みの後へ直列化し、入力を失わない。タイマーが遅れた場合は、実行時点の保存済みの状態を記録する。

正常なファイル終了と過去閲覧への切り替えでは5分を待たず未記録分を残す。履歴管理だけの変更は新たな業務データ変更として記録しない。記録失敗では期限と元データを保持し、自動で書き込みを繰り返さず、次の保存成功または利用者の再試行で再開する。

タブ終了・再読み込み・強制終了で非同期書き込みの完了は保証できない。通常のデータ保存は既存どおり確定し、未記録の開始日時はファイルへ残るため、開き直した際に期限を確認できる。

## 閲覧・復元・削除

現在の計画と閲覧用の過去データは別の状態として保持する。共通の閲覧専用状態を各編集画面へ渡し、入力・保存・削除・並べ替えを禁止する。画面移動と種別の閲覧、図の移動・拡縮は維持する。切り替え時は編集部品を作り直し、前の編集内容や選択済み施策を別の時点へ持ち込まない。現在へ戻るだけなら登録前の下書きは保持する。

復元では選んだ計画全体のコピーに現在の履歴管理表を引き継ぐ。復元前の現在状態と復元した状態を追加し、データ保存と同じ失敗・競合確認を通す。成功後に現在の計画を置き換え、下書きと画面移動履歴を初期化する。失敗では閲覧中の過去データと現在の計画を維持する。

削除は識別子の集合か、指定日時より前の条件で行う。複数件の削除は一つの処理で確定し、対象が消えていた場合は部分削除しない。削除後は不要領域を詰め、計画本体・未記録期限・次の識別子を維持する。

## 実装境界と検証計画

1. `core/dataHistorySchema.ts`と`core/dataHistory.ts`で記録・検証・復元・削除を完結させる。初回記録、5分の境界、期限維持、全体復元、新しい履歴の保持、破損・年度違い・入れ子の拒否を通常テストで確認する。
2. `extension/planFile.ts`と`ExtensionPage.tsx`で実ファイルへの確定・競合・タイマー・終了を扱う。書込・確定失敗、保存許可、再試行と同時入力を確認する。
3. `DataHistoryPage`と`HomePage`に履歴入口・日時一覧・削除確認・過去閲覧・復元確認を設ける。広い画面と狭い画面で、すべての編集入口の禁止と通常閲覧を確認する。
4. 確認用データへ内容の異なる3時点を追加し、実ファイルの再読込と生成元の一致を検証する。既存の金額・集計・分類・手修正の確認条件を維持する。

必須の検証とコミット手順は[AGENTS.md](../AGENTS.md#検証と完了条件)に従う。サンプルの条件と確認範囲は[対応表](../samples/README.md#履歴の確認)で管理する。
