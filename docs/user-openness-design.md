# ユーザーへの仕組みの開示

製品方針の正本は[製品方針と要件](../REQUIREMENTS.md#ユーザーに開かれたアプリ)。この設計は、実際の計画の値を出さず、アプリの構造・計算・処理をアプリ内で確認できるようにする。

## 表示の役割

| ホームの表示 | 確認できること |
|---|---|
| 関連図 | 画面とマスタの業務上の関係。従来の画面への入口を保持する |
| 画面とデータ | 保存テーブル・項目・参照先と各画面の対応 |
| 計算の仕組み | 入力から結果までの規則、条件・例外、結果を保存するかどうか |
| 処理の流れ | 操作と自動処理の契機、処理順、成功・失敗、保存場所と情報の寿命 |

既存の表示を維持し、役割が不足する計算・処理の表示を追加する。各表示はホーム内で切り替え、他の業務画面へ説明欄を追加しない。

## 内容と画面構成

計算の対象は金額精度、予算引き継ぎ、科目属性、総原価表と差、集計と利益率、四半期・半期・年間の合計、展開表、明細、開始年月、分類の絞り込み。
処理の対象は読込・新規作成、入力から自動保存、失敗と競合、時点履歴、操作取消と画面移動、保存場所、入力と参照関係の検証。

対象を選ぶと、元になる情報、番号付きの処理順、条件と例外、結果、どこに残るかを表示する。説明に対応する実装ファイルは折り畳んで確認できる。専門的な保存名は必要な場所で併記し、コードを読まなくても作用が分かる日本語を先に示す。

仕組み表示には計画の内容、ファイルハンドル、保存コマンドを渡さない。表示切り替えや閲覧で計画を変更せず、閲覧が取消・時点履歴を作らない。幅が狭いときは列を縦に並べ、表示領域内でスクロールする。

## 更新の正本と確認

構造は保存形式の正本から自動生成する。計算・処理の説明は実装に照合した静的な定義とし、対象ごとに根拠となる実装ファイルを対応づける。その実装と静的な参照先、説明の変更を検出し、照合した確認記録がなければ開発起動・型検査・ビルド・通常テストを停止する。

確認記録を更新する前に、説明の入力、処理順、条件、結果、保存範囲を実装と照合する。画面の対応と計算・処理の説明は、それぞれの確認コマンドで記録し、最後に通常の検証で両方を確認する。ハッシュの一致は説明の正確さを自動証明しない。説明対象の追加や削除も確認する。

## 実装と検証の計画

1. 計算・保存・履歴・状態管理の現在の実装を読み、開示対象と条件・例外を定義する。
2. 計画データに依存しない説明定義と共通表示を作り、ホームの切り替えへ接続する。
3. 実装との対応と説明更新漏れの検証を追加し、開発コマンドへ組み込む。
4. 要件と利用・更新手順を反映する。サンプルに新しい実データは不要で、既存の確認用計画で全表示を試す。
5. 自動検証で対象漏れ・更新漏れ・存在しない参照を確認する。画面で各対象・切り替え・狭い幅・キー操作・計画を変更しないことを確認する。
6. 並行作業の変更を含めず、版・配布物とともに通常コミットする。
